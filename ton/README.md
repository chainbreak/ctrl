# Ctrl · TAP и вход по NFT-номеру

Проект TON Blueprint для мессенджера Ctrl. Пользователь оплачивает номер токенами TAP, получает NFT на свой кошелёк и входит в профиль, подписав запрос в кошельке. После продажи публичный профиль номера переходит новому владельцу. Для личной переписки и прав сотрудников сервер выдаёт отдельный идентификатор владельца.

## 1. Сборка

Проверено на Windows с Node.js 26.13 и npm. Команды запускаются из корня распакованного проекта.

```powershell
npm ci
npm test
```

`npm test` компилирует FunC через Blueprint, затем запускает TON Sandbox и тесты HTTP API. Отдельно собрать контракты можно командой `npm run build`. Актуальные BOC находятся в поле `hex` файлов `build/*.compiled.json`.

| Файл | Назначение |
| --- | --- |
| `contracts/tap/jetton-minter-discoverable.fc` | Master TAP, эмиссия администратором, учёт предложения, адрес кошелька владельца |
| `contracts/tap/jetton-wallet.fc` | Кошелёк TEP-74, переводы, уведомления, сжигание и обработка возврата |
| `contracts/collection.fc` | Регистратор номеров и отдельные коллекции подарков с ценой в TAP |
| `contracts/nft/nft-item.fc`, `resolver.fc` | Владение, передача TEP-62, версия владельца и DNS-запись |
| `wrappers/protocol.cjs` | Начальное состояние, метаданные TEP-64, кодирование операций |
| `scripts/deploy.ts`, `edition.ts`, `trade.ts` | Развёртывание, выпуск серий, оплата, покупка, передача, вывод |
| `backend/proof.mjs`, `chain.mjs`, `auth.mjs` | Проверка подписи, чтение TON и управление сессиями |

## 2. Выпуск TAP и коллекций

TAP использует девять десятичных знаков. Master создаёт индивидуальные Jetton-кошельки. Администратор может выпускать TAP, менять администратора и метаданные токена. В текущей конфигурации предложение не ограничено. Ключ для выпуска хранится у подписывающего кошелька. Сервис входа использует только публичные данные блокчейна.

Выбрана фиксированная цена. В примере номер стоит **10 TAP**, подарок «Облачко Cloudflare» — **3 TAP**. Цены задаются до развёртывания в `scripts/deploy.ts`. Цена и каталог входят в начальное состояние коллекции и определяют её адрес. Текстовые метаданные хранятся в сети. Для новой серии с изображением можно передать URI в `scripts/edition.ts`.

Команды ниже используют testnet. Для их выполнения нужен кошелёк с тестовыми TON на оплату комиссий. Каждую транзакцию подтверждает его владелец. Сначала запустите:

```powershell
npx blueprint run deploy --testnet --tonconnect
```

Сохраните напечатанные адреса `tap`, `numbers` и `gifts`. Команды ниже используют переменные PowerShell, в которые нужно подставить эти три адреса.

```powershell
$tap = 'адрес tap'
$numbers = 'адрес numbers'
$gifts = 'адрес gifts'
npx blueprint run trade --testnet --tonconnect mint $tap $numbers 25
npx blueprint run trade --testnet --tonconnect deposit $tap $numbers 10
npx blueprint run trade --testnet --tonconnect balance $tap $numbers
npx blueprint run trade --testnet --tonconnect number $tap $numbers +33300001234
```

Первую команду подписывает администратор TAP. По умолчанию токены получает подписант. Чтобы выпустить их другому покупателю, добавьте адрес его кошелька после суммы. Остальные команды подписывает покупатель. Дождитесь появления нужной суммы через `balance` перед покупкой. Газ оплачивается в TON отдельно от цены товара.

## 3. Покупка и передача

1. Кошелёк покупателя отправляет TAP в Jetton-кошелёк коллекции. Скрипт `deposit` указывает ненулевую сумму TON для доставки `transfer_notification`. Сторонний клиент должен передать такое же назначение и достаточную сумму уведомления. Перевод с нулевым `forward_ton_amount` не создаст запись о депозите в регистраторе.
2. Регистратор принимает уведомление только от своего Jetton-кошелька, адрес которого вычисляет из адреса коллекции, master TAP и кода кошелька. Сумма зачисляется отправителю, указанному этим кошельком.
3. Покупатель выбирает номер. Контракт проверяет формат, баланс и отсутствие индекса `SHA256(UTF8(полный номер с плюсом))`. Допустимы `+333` и восемь цифр либо `+999` и восемь цифр. Первичный выпуск `+999` подписывает администратор коллекции. Дальнейшая передача возможна по стандарту TEP-62.
4. Списание цены, зачисление продавцу и запись о выпуске происходят в одной транзакции регистратора. Попытка купить занятый номер сохраняет TAP покупателя на его балансе. Если сообщение инициализации NFT не дошло, `recover` повторяет доставку ранее записанного выпуска. После перепродажи эта операция не меняет владельца.
5. Способ оплаты подарка тот же. В одной серии у каждого экземпляра отдельный последовательный индекс. В отдельную серию можно вынести бейджи или стикеры. Выручку продавец и остаток покупатель выводят со своего баланса командой `withdraw`.

```powershell
npx blueprint run trade --testnet --tonconnect deposit $tap $gifts 3
npx blueprint run trade --testnet --tonconnect gift $tap $gifts
$recipient = 'адрес кошелька получателя'
npx blueprint run trade --testnet --tonconnect transfer $tap $numbers +33300001234 $recipient
npx blueprint run trade --testnet --tonconnect withdraw $tap $numbers 2
npx blueprint run edition --testnet --tonconnect $tap 5 'Клавиша Ctrl' 'ipfs://<CID>/ctrl.png'
```

Укажите адрес получателя в `$recipient`, а в URI серии — CID опубликованного изображения. Пример вывода предполагает остаток минимум 2 TAP. Для передачи подарка укажите его коллекцию и десятичный индекс вместо номера. Для повторной инициализации используйте `trade ... recover <master> <collection> <индекс>`. Контракты и кошельки примера работают в базовой рабочей цепочке TON (workchain 0).

`dnsresolve` коллекции принимает цифровую метку без знака плюса и делегирует её NFT. Резолвер элемента возвращает запись категории `wallet` с текущим владельцем. Публикация такого пространства имён в глобальной TON DNS требует отдельно настроить делегирование от родительского домена. Перепродажа поддерживается стандартным сообщением `transfer`. При помещении NFT в эскроу владельцем на время сделки будет смарт-контракт эскроу.

## 4. Вход по номеру

1. Экран отправляет `POST /auth/challenge` с полем `number`. Сервер создаёт 32 случайных байта и сохраняет хеш запроса, номер и срок действия в SQLite. Запрос действителен пять минут.
2. TON Connect передаёт запрос как `tonProof` в кошелёк. Кошелёк подписывает сообщение домена Ctrl. На сервер приходят адрес, сеть, номер и объект `proof`.
3. `POST /auth/verify` проверяет сеть, точное имя домена, его длину и время. Сервер берёт код и состояние активного кошелька из TON, определяет V4R2 либо V5R1 и извлекает открытый ключ. Для V5R1 дополнительно требуется включённая авторизация подписью. Затем сервер проверяет подпись Ed25519 формата `ton-proof-item-v2`.
4. На том же блоке сервер вычисляет индекс номера, вызывает `get_nft_address_by_index` у настроенного регистратора и `get_nft_data` у найденного элемента. Проверяются инициализация, индекс, коллекция и владелец. Имя в метаданных само по себе не даёт доступа.
5. После успешной проверки сервер атомарно погашает запрос и сохраняет сессию. Выдаётся JWT на 30 минут. Повтор той же подписи, в том числе параллельный, не создаёт вторую сессию.
6. `GET /auth/me` принимает `Authorization: Bearer <JWT>`. Перед выдачей данных сервер снова сверяет владельца и версию владения в TON. Дополнительно он проверяет активные сессии каждые 30 секунд. NFT увеличивает версию при каждой смене владельца: даже если номер продали и вернули между проверками, старая сессия теряет доступ. Если RPC недоступен, защищённый запрос получает HTTP 503. Выход через `POST /auth/logout` отзывает конкретную сессию.

### Настройка сервиса

```powershell
Copy-Item .env.example .env
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Запишите полученное значение в `JWT_SECRET_HEX`. Укажите в `NUMBERS_COLLECTION` точный адрес регистратора номеров из шага 2. `PUBLIC_ORIGIN` должен совпадать с HTTPS-адресом страницы, включая нестандартный порт, без пути и завершающего слеша. `TON_NETWORK` и доверенный `TON_V4_ENDPOINT` должны указывать на одну сеть. Для testnet используется `-3`, для mainnet — `-239`.

```powershell
npm run auth
```

HTTP-процесс слушает `BIND_HOST:PORT`. HTTPS-прокси на `PUBLIC_ORIGIN` должен направлять к нему запросы. Кошельку нужны доступные по этому адресу `/tonconnect-manifest.json` и `/icon.png`. Откройте страницу, введите уже выпущенный номер и подтвердите запрос в активном V4R2 или V5R1. Ограничитель запросов сервиса считает попытки по IP прямого подключения. При общем прокси отдельные лимиты для клиентов настраиваются на самом прокси.

### Подключение к API мессенджера

Сервис входа поставляется отдельно от Windows-клиента 2.5.0. Для чата его сервер должен перед защищённой операцией отправить JWT на `GET /auth/me` и использовать ответ только при HTTP 200. Ответ содержит `subject` для переносимого публичного профиля и `privateSubject` для личных диалогов текущего владельца. Прежние личные сообщения и должностные полномочия не переходят покупателю номера. Роли руководства и поддержки назначаются самим мессенджером. Префикс `+999` не является полномочием.

При HTTP 401 клиент запрашивает новый вход, при HTTP 503 предлагает повторить запрос. Для открытого канала доставки сообщений нужно также перепроверять сессию перед выдачей данных. Постоянная сессия чата, созданная после единственной проверки JWT, обошла бы отзыв по смене владельца.

## Что проверено

Тесты используют настоящие подписи Ed25519, кошельки TON и исполнение скомпилированных контрактов в TON Sandbox. Сквозной тест выпускает TAP, покупает NFT, авторизует владельца, передаёт номер второму кошельку и проверяет доступ обоих. Отдельные тесты покрывают DNS-запись, поддельное уведомление о платеже, занятый номер, подарок, вывод TAP, повтор подписи, сбой RPC и HTTP-маршруты. Публичный деплой, подтверждение в мобильном Tonkeeper и интеграция с интерфейсом Getgems не выполнялись.
